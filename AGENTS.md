# Правила общения с владельцем проекта

- Владелец проекта не является программистом. Его технический уровень —
  уверенная работа с Excel, но без знания разработки и инфраструктуры.
- Объясняй решения простым русским языком и начинай с практического результата.
- Не используй без пояснения слова вроде «коммит», «ветка», «деплой», «API»,
  «контейнер», «миграция», «линтер» и другой профессиональный сленг.
- Если технический термин необходим, сразу объясни его одной простой фразой.
- Не требуй от пользователя самостоятельно выполнять технические команды, если
  Codex может безопасно выполнить их сам.
- После изменений всегда явно указывай один из статусов:
  - изменения сделаны только локально и ещё не видны посетителям сайта;
  - изменения опубликованы на рабочем сайте и проверены.
- В отчёте сначала перечисляй, что изменилось для пользователя сайта. Технические
  подробности добавляй только при необходимости.
- Не называй пользователя глупым и не повторяй самоуничижительные формулировки.
  Терпеливо объясняй любые базовые понятия без предположения о предварительных
  знаниях.

# Обязательные правила проекта

- Перед любым изменением кода прочитай и соблюдай все файлы из
  [`.codex/rules/`](.codex/rules/).
- Правила в `.codex/rules/` обязательны для нового кода, рефакторинга,
  тестирования и публикации.
- Если изменение требует отступить от правила, не создавай скрытое исключение.
  Сначала объясни владельцу причину и получи его явное согласие.

# Экономия времени, инструментальных вызовов и контекста

- Этот порядок обязателен для каждой следующей задачи в проекте, включая новые
  чаты. Он хранится в файлах проекта и не зависит от памяти переписки.
- Соблюдай [правило 09](.codex/rules/09-efficient-work.md): работай автономно,
  сообщай только о критических проблемах, необходимости решения владельца и
  окончательном результате.
- Ограничивай изменения запросом владельца и необходимыми для него исправлениями.
  Не добавляй попутную перестройку соседних разделов.
- По [правилу 05](.codex/rules/05-testing-and-refactoring.md) локально проверяй
  изменённые области. Единственный штатный полный прогон выполняется в GitHub
  перед публикацией; не дублируй его целиком на компьютере без конкретной причины.
- Не повторяй проверки, сборки и чтение неизменённых файлов без причины.
  Экономия не отменяет обязательные проверки и проверку рабочей базы.
