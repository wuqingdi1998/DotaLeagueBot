# Архитектура сайта

Обязательные архитектурные требования закреплены отдельными правилами в
[`../.codex/rules/`](../.codex/rules/). Этот документ объясняет текущую
структуру сайта, но при расхождении источником требований являются файлы из
`.codex/rules/`.

Этот документ задаёт обязательные правила для новых изменений. Его цель —
сделать проект предсказуемым: изменение одной части страницы не должно случайно
ломать другую.

## Основной принцип

Код организуется по пользовательским возможностям, а не по типу файлов.
Например, всё, что относится к странице одного турнира, находится рядом:

```text
app/tournaments/[slug]/
├── page.tsx                 # только вход на страницу
├── TournamentPage.tsx       # сборка крупных блоков страницы
├── model/                   # типы, правила и преобразование данных
├── services/                # обращения к серверу
├── hooks/                   # состояние и сценарии страницы
├── components/              # общие элементы страницы турнира
├── sections/                # независимые пользовательские разделы
└── admin/                   # инструменты организатора
```

## Границы ответственности

- `page.tsx` не содержит бизнес-логику и большое оформление. Он только подключает
  готовую страницу.
- `model` не зависит от React и браузера. Эти функции проще всего тестировать.
- `services` знает адреса серверных запросов, но не знает, как выглядит экран.
- `hooks` управляет состоянием и объединяет пользовательские сценарии.
- `components` содержит небольшие переиспользуемые элементы без знания всей
  страницы.
- `sections` получает готовые данные и обработчики, затем показывает один
  законченный раздел.
- `admin` отделён от публичной части турнира.

Зависимости направлены сверху вниз:

```text
page → sections/hooks → services/model
                   ↘ components
```

Нижний слой не импортирует верхний. Общий компонент не должен импортировать
целую страницу.

## Размер файлов

- Целевой предел для TypeScript, TSX и CSS — 500 строк.
- Превышение допустимо только временно во время разделения старого кода.
- Если файл приближается к пределу, его делят по законченной ответственности,
  а не на случайные куски.
- Входной файл страницы обычно занимает не более 50 строк.

## Переиспользование

- Повторяющийся визуальный элемент выносится в `components`.
- Повторяющееся преобразование данных выносится в `model`.
- Повторяющийся запрос выносится в `services`.
- Компонент создаётся заново только тогда, когда у него действительно другое
  поведение, а не только другой текст или цвет. Варианты передаются параметрами.
- Числа, статусы, роли, адреса запросов и другие правила не размазываются по
  странице: у них должен быть один источник.

## Стили

`globals.css` содержит только подключения файлов. Стили разделены в том же
порядке, в котором они применяются:

```text
app/styles/
├── foundation/       # шрифты, переменные, сброс стандартного оформления
├── shared/           # шапка, кнопки, окна, общие карточки
├── tournament/       # публичная страница турнира
├── tournament-admin/ # управление турниром
└── pages/            # самостоятельные страницы сайта
```

- Стили конкретного раздела лежат рядом с его областью ответственности.
- Мобильные правила находятся в том же файле, что и основной элемент.
- Селекторы не зависят от случайного положения элемента в разметке.
- Новое правило не должно исправлять старое через длинную цепочку переопределений.
- Порядок подключений меняется только осознанно, потому что более позднее правило
  может иметь приоритет.

## Данные и отсутствие жёстко заданных значений

- Турнирные тексты, даты, лимиты, форматы и статусы берутся из данных турнира.
- Допустимые значения описываются типами и общими константами.
- Часовой пояс, ограничения формы и серверные адреса имеют именованный источник.
- Тестовые данные не попадают в рабочий интерфейс.

## Самодокументируемый код

- Имена отвечают на вопрос «что это делает», а не «как это написано».
- Функция выполняет одно действие и возвращает предсказуемый результат.
- Булевы значения начинаются с `is`, `has`, `can` или `should`.
- Комментарий объясняет причину или нестандартное правило. Он не пересказывает
  очевидную строку кода.
- Для неочевидной публичной функции используется JSDoc-комментарий: короткое
  описание входных данных, результата и важного ограничения.

## Защита от поломок

Перед структурным изменением фиксируется текущее поведение тестами. После каждого
этапа обязательно выполняются:

1. автоматические тесты;
2. проверка типов;
3. проверка качества кода;
4. полная сборка сайта;
5. визуальная проверка ключевых экранов на компьютере и телефоне, если менялась
   разметка или оформление.

Структурный рефакторинг не должен одновременно менять пользовательское поведение.
Новая возможность добавляется отдельным следующим изменением.
