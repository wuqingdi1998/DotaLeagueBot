# Правило 05. Тестирование и безопасный рефакторинг

## До рефакторинга

- Сначала зафиксируй текущее пользовательское поведение базовыми тестами.
- Покрой ключевые сценарии, границы модулей, преобразования данных и контракты
  между клиентом и сервером.
- Если поведение невозможно надёжно проверить автоматически, опиши и выполни
  воспроизводимую ручную проверку до изменения.

## Во время рефакторинга

- Структурный рефакторинг не должен одновременно менять пользовательское
  поведение.
- Новую возможность или изменение дизайна выполняй отдельным следующим
  изменением.
- Делай перенос по законченным модулям, сохраняя рабочее состояние после каждого
  этапа.
- При обнаружении незафиксированного важного поведения сначала добавь тест, затем
  продолжай перенос.
- Не удаляй защитный тест только потому, что новая структура его не проходит.
  Исправь код или обоснованно обнови контракт поведения.

## Обязательная проверка после изменения кода

### Локально: изменённые области

- Сначала определи затронутые пользовательские сценарии и выбери связанные с ними
  тесты. При изменении доступа проверь роли, при изменении запросов или начислений
  — разделение периодов, целостность данных и чтение рабочей базы без записи.
- Проверь типы и качество изменённого кода. Если инструмент работает только со
  всем проектом, допустим его отдельный общий запуск без запуска остальных этапов.
- При изменении разметки или стилей проверь затронутые экраны на компьютере и
  телефоне. Полный набор всех экранов локально повторять не требуется.
- Сначала закончи запланированные правки. Локальную рабочую сборку запускай,
  только если она нужна для проверки изменённого поведения или ошибки сборки.

### Один полный прогон: GitHub перед публикацией

Штатный полный прогон выполняется в задании `validate` процесса
[`.github/workflows/deploy.yml`](../../.github/workflows/deploy.yml) для отправленной
версии. Он завершается до установки этой версии на рабочий сайт. Его успешный
результат выполняет требование полной проверки перед публикацией.

Не запускай заранее `scripts/check.ps1`, `npm run check` и весь набор визуальных
проверок только для повторения того же полного прогона на компьютере. Локальный
полный прогон допустим по прямому запросу владельца, при недоступности GitHub или
для воспроизведения ошибки, которую нельзя проверить точечно. Укажи конкретную
причину; такой запуск не отменяет обязательные проверки GitHub.

После ошибки сначала исправь её и повтори соответствующую локальную проверку.
Если код изменился, GitHub должен полностью проверить новую отправленную версию.
Результат предыдущей версии нельзя объявлять проверкой новой. Без изменений кода
и без ошибки не повторяй уже успешные проверки и сборки.

Если меняется только документация или инструкции для работы, проверь текст,
ссылки и состав изменений. Тесты и сборка приложения нужны, только если эти файлы
используются при его сборке или исполнении. Обязательные проверки, автоматически
запущенные GitHub, должны завершиться штатно.

Полный прогон и последующая проверка опубликованного сайта сохраняют все этапы:

1. Автоматические тесты.
2. Проверка типов.
3. Проверка качества и единообразия кода.
4. Полная рабочая сборка.
5. Проверка архитектурных ограничений, включая предел размера файлов.
6. Визуальная проверка ключевых экранов на компьютере и телефоне, если менялись
   разметка или стили.
7. После публикации — проверка публичного сайта и его служебного адреса
   работоспособности.

Ни один этап нельзя отключать, обходить или объявлять успешным без фактического
результата.
