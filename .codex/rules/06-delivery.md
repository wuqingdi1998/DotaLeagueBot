# Правило 06. Тестовый сайт и публикация без обходов

## Два сайта

- Основной сайт: `https://lsesports.ru`, версия из `main`.
- Тестовый сайт: `https://dev.lsesports.ru`, версия из `codex/dev`.
- Компендиум на тестовом сайте отключён по решению владельца: его страницы,
  архив и серверные запросы там недоступны. Не включай его без новой команды владельца.
- Новые обновления по умолчанию сначала устанавливаются на тестовый сайт.
- На основной сайт переносить обновления только по явной команде владельца
  опубликовать проверенную версию. Запрос изменения сам по себе не означает
  разрешение сразу обновлять основной сайт.
- Первоначальная настройка тестовой среды включает запрошенную владельцем
  установку её инфраструктуры и служебного номера версии на основном сайте.

## Обязательный процесс

1. Закончи весь запланированный набор изменений и выполни точечные локальные
   проверки по правилу 05.
2. Убедись, что все относящиеся к задаче новые и изменённые файлы добавлены в
   Git.
3. Сохрани весь законченный набор изменений в Git с понятным описанием.
4. Отправь его в `codex/dev` репозитория GitHub. Описание сохранения пиши по-русски,
   называя пользовательский результат: оно попадает в список отличий «DEV · i».
5. Дождись полного прогона `validate` и успешного задания `development` в
   `.github/workflows/deploy.yml`. Отдельный полный локальный прогон не требуется.
6. Проверь тестовый сайт, `/api/health`, `/api/version`, защиту от входа посторонних
   и список отличий. Явно сообщи, что обновлён тестовый сайт, а основной ещё не менялся.
   После явной команды владельца перенеси проверенный набор в `main` с сохранением
   истории (`fast-forward`, если возможно). Не объединяй историю в один новый
   снимок: сравнение версий опирается на исходные номера изменений.
   Дождись `validate` и задания `deploy`, проверь основной сайт и его служебные
   адреса. После публикации продолжай новые работы в `codex/dev`.
7. Убедись, что локальная папка не содержит забытых изменений и совпадает с
   отправленной версией.

## Разделение данных

- Тестовый сайт использует отдельную базу, отдельные файлы и отдельные входы.
- Первоначальная копия рабочей базы создаётся только чтением. Последующие
  обновления сохраняют пробные данные, а не заменяют их свежей рабочей копией.
- При публикации переносится программа. Тестовые результаты, настройки и файлы
  не переносятся в рабочую базу.
- Рабочий Discord-бот в тестовой среде не запускается; его токен и доступ к рабочей
  базе туда не передаются. Discord-вход отдельно не настроен: используется
  существующий вход по паролю организатора.
- Скопированные рабочие сеансы и временные пароли очищаются до открытия тестового сайта.

## Запрещено

- Оставлять завершённую работу только локально, если владелец прямо не попросил
  не публиковать её.
- Копировать или редактировать рабочие файлы непосредственно на сервере.
- Вручную перезапускать рабочую систему вместо штатного GitHub Actions.
- Отключать или пропускать проверки.
- Использовать `--no-verify`, `force push`, временные хаки и другие обходы
  стандартного процесса.
- Выдавать локальную или тестовую версию за опубликованное обновление основного сайта.

## Если публикация не прошла

- Найди первопричину ошибки в штатном процессе.
- Исправь её в исходном коде или настройках проекта.
- Повтори затронутые локальные проверки; новая отправленная версия должна пройти
  полный прогон GitHub.
- Сохрани исправление в Git и снова отправь его в GitHub.
- Не исправляй рабочий сервер вручную.
